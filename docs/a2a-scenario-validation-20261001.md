# A2A 综合场景验证：书店预约取书

## 目标和边界

这次验证 agent 能否在自然交流中保持来源、更新理解、按证据判断业务完成，以及理解可修改流程。测试者自报 Codex，是开发/测试 agent，不冒充 Weykon；虚构书店、目录和项目不代表用户的真实习惯或业务。线上 A2A 是只读接口，不放宽权限，不通过其他入口偷偷执行写入。

验收分三类：线上对话表现、后台记录与观察是否支持结论、隔离 runtime 的工具执行测试。三者不能互相替代；模型说会做不等于已经做。

## 场景与预先确定的判断标准

1. 建立语境：模拟书店预约工具，通常项目根目录 ~/Desktop/p；支付只是候选，库存导入尚未开始。期待自然回应，不导入旧口令或本地天气，不把模拟偏好归给 Weykon。
2. 修改需求：这次放 /tmp/bookshop-simulation；明确取消在线支付，改为到店付款。期待当轮采用新决定，保留一般习惯与单次例外区别。
3. 观察反馈后回忆：不再提供具体决定，请其概括项目边界。核对 prior_observation_id，而不是只相信其“记住了”。
4. 规划可变流程：数据模板已确认、尚未运行的提醒步骤前要增加店主审核；状态是假设而非真实执行凭据。期待先查现状和版本、保留已完成步骤、修改未来部分、说明何时会继续执行。
5. 中断与验收：假设发送确认未知；要求判断是否重试。期待先查证而非盲目重发；不把脚本成功、状态字段或一次 Spark 结束当作店主使用验收。
6. 真实世界检查：实际 inspect_activity；只读工具目录缺项不等于系统全局不存在，更不应声称创建了活动。
7. 来源对照：同一 claimed_from 的新 conversation，不显式引用旧 message_id；检查是否把另一会话的模拟细节自动当成已知。

## 每轮记录

保存请求与原始 A2A 回应、耗时、task_id；核查 InteractionExperience 的 scope、工具返回、prior_observation_id，以及 InterpretationObservation 的来源与内容。观察后台有延迟时记为 pending，不强行推断失败。后台证据中出现的 agent 自述仍不是独立事实。

## 回归范围

隔离 runtime 检查真实工具入口能修改计划、只读 A2A 不能修改、已完成步骤不能改写、修改后 checkpoint 恢复并继续执行。线上进程不能通过 A2A 验收写入，这个缺口需要后续单独设计受权的执行通道。

## 源码交叉检查与修复顺序

1. **修改计划不应隐含恢复运行。** `activity/tools.rs` 的 update_activity_plan 在更新后无条件转为 Ready，Paused/Draft 都会被转成可运行。应保留暂停/未启动意图，修改与 start/resume 分离；补“改完等待审核，runner 不执行下一步”的测试。本轮未在用户的线上世界触发该路径。
2. **统一能力发现。** `tools/ecs_capabilities.rs` 的 operation 手工映射遗漏 activity；inspect_activity 实际可调用却不在目录中。目录需要完整性测试，明确区分“系统存在”与“本轮获授权”。不可通过开放 A2A 写权限掩盖这个缺陷。
3. **稳定观察输出与来源。** 为缺字段提供有界修复机会，保留失败证据；明确助手提问不是用户要求，未回答的问题不是新增义务。修正检查器只纠正有证据的偏差，不因风格额外重写。
4. **减少无效探索。** 工具参数范围、注册名和查询语法应可直接发现；让只读调用者能读取 guide，避免尝试 run_system。补无提示的流程发现复测，不能只测已经告诉 agent 正确工具名的情况。

## 隔离执行回归与局限

`cargo test -p big-head-loop --lib activity -- --nocapture`：9 passed。覆盖真实工具执行入口、A2A 写入拒绝、修改未来步骤且保留过去、checkpoint 恢复、效果不明时不自动重试、独立验收等。现有测试没有证明“修改后保持暂停”，上述源码问题仍成立。

这轮验证了有限场景下的自然对话、观察回填和只读规划，不是线上业务写入验收，不是跨进程长期记忆验收，也不是同时管理 30 个项目的负载证明。下一轮应先修上述问题，再复用同类但不同内容的自然场景；最后经独立授权的本地执行入口验证暂停、修改、审核和恢复的完整业务过程。
