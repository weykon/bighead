# 业务活动运行层：方案与验收

目标：区分模型一轮结束、工具执行成功、业务目标经证据验收完成。ECS 保存状态；运行层维护推进、等待、恢复和验收规则；业务组件、规则和 Rhai system 保持动态定义。

## 第一阶段：可恢复的最小活动闭环（本次实现）

- `ActivityRun` 是运行基础设施，包含不可变计划、稳定业务键、版本、当前步骤、生命周期、执行记录和读取证据，不内置订单、项目或审批业务类型。
- 工具负责创建、启动、暂停、恢复、取消、检查和故障后的重新验收。创建使用 scope + id 去重，相同请求复用，不同计划拒绝覆盖；控制操作检查 revision。
- agent 可在 Draft、Paused 或已明确非不确定的 Blocked 状态修改未来计划；`update_activity_plan` 重新校验步骤和系统 hash，保留旧 plan_history，禁止改写已完成步骤、运行中步骤和不确定副作用。
- 修改后保持原来的 Draft/Paused/Blocked 状态，不能隐含启动或恢复授权。审核通过后必须携带新 revision 单独 start/resume；暂停状态跨 checkpoint 恢复仍保持。
- 主循环每次至多推进一个活动步骤，不调用 LLM。第一种执行适配器是已注册且代码 hash 固定的 Rhai system。
- 前置条件不满足时等待；步骤执行后独立读取 ECS 验证；最后检查活动目标。不存在“直接把状态改成 completed”的工具。
- 检查通过组件上的稳定业务字段定位对象，不持久化临时 entity index；匹配零个或多个对象均不能通过验收。
- 执行前保存 Running，再执行，再保存结果。恢复遇到 Running 转 Blocked，要求重新读取证据，禁止自动重复有潜在副作用的步骤。
- 暂停/取消不承诺撤回已经发生的效果。失败也不承诺全局事务回滚。重新验收证明当前状态满足条件，不证明外部副作用恰好执行一次。
- 验收：动态业务组件、两步 Rhai、等待外部字段、checkpoint 恢复、最终目标检查、重复请求、错误 hash、执行失败、未知执行结果、只读权限隔离。

已通过的运行验证：两次计数活动先执行第一步，等待批准，保存并恢复 runtime 后执行第二步，再独立确认目标；模拟订单活动等待 paid=true 后更新 fulfilled 并读回。两个领域共用同一运行器，没有引入业务 Rust 类型，也没有调用模型推进步骤。

故障测试覆盖：重复计划复用、不同计划拒绝覆盖、版本冲突、暂停取消、代码变化阻断、目标未达成、重复业务键拒绝、执行后抛错、保存失败、运行中断恢复、超期、无限脚本预算终止，以及 A2A 只读调用者不能启动活动。运行器在已有 Spark 排队时让出。

源码入口：`crates/big-head-loop/src/activity/`。模型按需读取 `run_system("guide_activity")`，工具入口是 create_activity/control_activity/inspect_activity。主循环在 TickAction 评估后推进至多一步。尚未在用户当前运行进程中验收新版本；需要重启加载本次代码。

## 第二阶段：调度和执行隔离（后续里程碑）

目前主循环仍会等待前台 LLM 和同步 Rhai；“每次推进一步”不等于抢占式调度。后续把事件接收、运行协调、长耗时适配器拆开；执行器返回任务句柄，事件携带 run/step/attempt 身份；主线程负责状态提交。

验收：模型请求持续 30 秒时，事件仍可排队，短后台工作继续推进；单一项目不占满其他项目预算；取消、超时、迟到回调都能确定归属，不覆盖新版本。

## 第三阶段：更多执行和证据适配器（后续里程碑）

增加文件存在/内容、构建退出码、测试报告、服务端回执等独立验收；CLI 和远端操作使用幂等键或查询恢复协议。不支持幂等的效果中断后停待处理。补偿是显式业务步骤，不伪装成自动数据库回滚。

验收：coding 项目和模拟订单两个不同领域复用同一运行器；审批等待、外部失败、补偿和恢复有证据；agent 只在需要规划或解释时介入。

## 自然交流与活动的边界

闲聊无需创建活动；已明确的持续工作可形成活动。解释/Lens 可以帮助拟定计划，但不能冒充执行凭据。agent 可用 inspect_activity 获得事实再回答，无需向用户复述内部状态名。自动从每句话创建活动、通用 DAG、外部恰好一次执行，都不属于第一阶段完成声明。
